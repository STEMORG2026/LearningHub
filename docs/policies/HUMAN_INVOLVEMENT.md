# Human Involvement in the Development Process

**Version:** 3.0.0
**Status:** Active
**Owner:** Architecture
**Applies To:** Release pipeline, docs ownership, decision authority
**Related:** `RULES.md`, `VERSIONING.md`, `AGENTS.md`

## The one-line rule

**Human decides what is true and what is worth releasing. Automation records, synchronizes, verifies, versions, commits, and tags it.**

Never bypass the release approval boundary. Never manually edit machine-owned generated sections.

## 1. Normal development

During ordinary feature work, bug fixes, refactoring, and testing:

1. Human or agent implements the work.
2. Run the appropriate tests and governance checks.
3. Commit normally.

The pre-commit hook automatically runs `docs:sync` and `sync-versions`, then stages deterministic documentation changes.

Create a Changeset whenever package work should be included in a future release. A Changeset records release intent (patch/minor/major) — it does **not** trigger an immediate release. Changesets accumulate until you deliberately decide to release.

You normally do **not**:

* bump package versions;
* create release tags;
* run the release pipeline;
* manually maintain generated `AUTO` sections;
* manually update generated `Version:` headers.

A normal development commit does not constitute a release.

## 2. Phase completion

A phase contains multiple features, fixes, refactors, tests, and integration work.

Only when the **entire phase** is genuinely complete should its status be changed in `.phase.json`:

```json
"status": "completed",
"completedVersion": null,
"completedDate": null
```

Leave `completedVersion` and `completedDate` as `null`.

The release pipeline fills those values when the phase is formally released.

Never infer phase completion merely because code changed or tests passed. Phase completion is a human decision.

## 3. Release

The only official release workflow is:

```text
pnpm release:prepare
        ↓
human review / approval
        ↓
git add -A
        ↓
pnpm release:validate
        ↓
pnpm release:version
        ↓
pnpm release:finalize
```

There is no `release:complete`.

After `pnpm release:prepare`, the agent must stop for human review.

The human must:

1. Review the release candidate.
2. Refine the root `docs/CHANGELOG.md` narrative when needed.
3. Write/refine human sections of `docs/DEVLOG.md`.
4. Remove all `[EDIT: ...]` markers.
5. Resolve semantic or ambiguous warnings.
6. Confirm the phase state is correct.
7. Explicitly approve the release candidate.
8. Run `git add -A`.

`git add -A` is mandatory, not optional: it establishes the human-approved staged baseline that `release:validate` fingerprints with `git write-tree`. `release:validate` refuses to run while the tree is dirty or `[EDIT: ...]` markers remain.

Only after approval should the validation/version/finalization stages proceed.

**Finishing implementation is not release approval.**

Note: `release:finalize` ends with its own `git commit`, which triggers the pre-commit hook again. This is intentional and harmless — `docs-sync` is idempotent, so the second run produces no further changes.

### 3a. Docs-only release

A docs-only release happens when a phase is explicitly completed and **zero Changesets** exist:

* no package version bump;
* no package tags;
* the release commit still records phase completion and documentation;
* the commit uses the docs-only release convention.

This is a valid release path. It does not version anything — it formally records that the phase is complete and releases its documentation.

## 4. Version choice

The human decides the release impact in the Changeset:

* `patch`
* `minor`
* `major`

Automation applies the declared versioning decision. It does not guess semantic versioning.

## 5. Human-owned vs machine-owned documentation

### Machine-owned / deterministic

These are maintained by automation:

* `ROADMAP.md` deterministic `AUTO` sections
* `AGENTS.md` phase/package `AUTO` sections
* deterministic testing information
* generated version headers
* package CHANGELOGs generated by Changesets
* deterministic file/package references

Do not manually edit these generated sections. This includes the test counts in `docs/component-registry/TESTING.md`, which are machine-derived from the repository's test files on every `docs:sync` — hand-editing them is pointless because they get overwritten.

### Human-owned / semantic

These remain under human control:

* CHANGELOG narrative
* DEVLOG Notes, Struggles, and Learnings
* semantic or ambiguous component-registry decisions
* `docs/RULES.md`
* `docs/ARCHITECTURE/README.md`
* `docs/guides/COMPONENT_STANDARDS.md`
* `docs/policies/EVENT_BUS_CONTRACT.md`
* ADRs
* phase-completion decisions
* Changeset SemVer decisions

### Special case: RENDERING and STATE registry sections

`RENDERING.md` and `STATE.md` contain both generated and human-curated information. The precise ownership rule:

* **ROADMAP/AGENTS/TESTING deterministic `AUTO` sections:** never manually edit — automation regenerates them from repository state.
* **RENDERING/STATE newly-completed phase markers:** automation may overwrite/fill them during the completion/release transition. Human refinement of a newly-completed phase's entries happens **only after** the phase is released.
* **Once RENDERING/STATE content represents a released/historical phase:** automation must preserve that human-curated content and must not regenerate it wholesale. Human semantic refinement of released phases is allowed.

## 6. One-time setup for a new clone

Run:

```bash
pnpm install
pnpm setup-hooks
```

`setup-hooks` configures:

```text
core.hooksPath = scripts/git-hooks
```

Without this setup, the repository's pre-commit synchronization hook will not run.

## 7. Before ordinary commits

Check:

* Is a phase actually complete? If yes, update `.phase.json` and leave release fields `null`.
* Did I accidentally edit a machine-owned `AUTO` section?
* Are tests/governance appropriate for the change?

Then commit normally.

## 8. Before a release

Check:

* Did I create the required Changesets? (Or, for a docs-only release, are there intentionally zero Changesets with a phase marked complete?)
* Did `release:prepare` complete?
* Did I review the generated release candidate?
* Did I remove every `[EDIT: ...]` marker?
* Did I resolve semantic warnings?
* Did I explicitly approve the release?
* Did I run `git add -A`?

Then run the four-stage pipeline.

## 9. What automation is responsible for

Automation is responsible for:

* deterministic documentation synchronization;
* version-header synchronization;
* governance verification;
* authoritative tests;
* Changesets version application;
* release documentation finalization;
* phase release metadata;
* release commit;
* release tags;
* validation-token handling.

Human judgment remains responsible for **meaning, completion, intent, and approval**.

## 10. The simplest mental model

```text
Development:
work → test → commit

Phase completion:
human decides → .phase.json status = completed

Release:
prepare → HUMAN APPROVAL → validate → version → finalize
```

The automation handles the bookkeeping and enforcement. The human decides what the project means and what is ready to become an official release.
